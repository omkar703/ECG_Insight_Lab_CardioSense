## 1. Executive Summary

Phase 8 successfully implements an end-to-end, safety-grounded **Explain Results** capability across all result-producing workflows in the CardioSense Streamlit application. When a user runs any classification, signal processing analysis, paper digitization, or offline hardware simulation, they can click **Explain Results ✨** to receive a plain-language explanation generated by the Groq API.

### Core Architectural Guarantees
1. **Explanation Layer Only:** The Groq language model acts strictly as an interpretation and translation layer. It **never** alters, predicts, overrides, or re-ranks physiological ECG scores, labels, or metrics. All numeric outputs remain 100% deterministic and originate solely from verified machine learning pipelines and digital signal processing routines.
2. **Strict Privacy Boundary:** Payloads passed to the Groq API are whitelist-filtered and sanitized. Raw ECG voltage arrays, scanned image pixels, patient identifiers, local directory paths, and environment secrets are **never** transmitted over the network.
3. **Medical Safety and Non-Diagnostic Mandate:** Every explanation is anchored by strict system instructions stating that CardioSense is an academic research software prototype and **not** a certified medical device. The model is forbidden from stating or implying clinical diagnoses.
4. **Frozen Model Integrity:** All pre-existing machine learning weights, feature extraction pipelines, and evaluation metrics remain untouched. The single-lead Random Forest model SHA-256 digest remains byte-for-byte identical (`3889a5f5ab97803da339710d4ae9fde8ea50f8e5a5ff76ed2015a0fb0b6ec8e9`).

## 3. Architecture and Implementation Details

The explanation system is implemented as a modular package located at `ecg_lab/explanations/`:

```
ecg_lab/explanations/
├── __init__.py           # Package exports (service, client, schemas, UI)
├── schemas.py            # Typed dataclasses (ExplanationPayload, ExplanationResult, WorkflowType)
├── groq_client.py        # Multi-source secret resolution, bounded retry, error sanitization
├── prompts.py            # Safety-grounded system prompt, workflow instructions, JSON schema
├── service.py            # Whitelist payload sanitizer, SHA-256 caching, fallback handling
└── ui.py                 # Streamlit UI helpers (render_explain_results_button, render_explanation_panel)
```

### 3.1 Multi-Source Secret Resolution (`groq_client.py`)
To ensure seamless deployment across local development, Docker containers, Streamlit Community Cloud, and academic servers, API keys are resolved in deterministic priority order:
1. Environment variable `os.environ["GROQ_API_KEY"]`
2. Environment variable `os.environ["GROQ_API"]` (accommodating existing user `.env` configurations)
3. Streamlit secrets `st.secrets["GROQ_API_KEY"]` or `st.secrets["GROQ_API"]`
4. Root workspace `.env` file via `dotenv.dotenv_values`
5. Parent workspace `.env` file

*Key Masking:* Any exception originating from network errors or API calls is sanitized via regex (`gsk_***` and `Bearer ***`) before being rendered in the UI or written to logs.

### 3.2 Active Model Configuration
- **Verified Active Model:** `qwen/qwen3.8-27b`
  - Cloud testing on Groq demonstrated sub-2.5 second latency for JSON-mode chat completions.
  - Full native support for structured JSON generation (`response_format={"type": "json_object"}`).
- **Model Overrides:** Configurable via environment variable `GROQ_MODEL` or Streamlit secrets without modifying application code.

### 3.3 Whitelist Payload Sanitization (`service.py`)
To prevent inadvertent leakage of patient records, file structures, or raw biometric arrays, `sanitize_payload()` enforces a strict whitelist filter:
- **Allowed Keys:** `schema_version`, `workflow`, `source_category`, `is_simulation`, `sampling_rate_hz`, `units_and_calibration`, `summary_metrics`, `class_predictions`, `data_quality_flags`, `evaluation_context`, `known_limitations`.
- **Sanitization Actions:**
  - Strips any key matching patterns such as `patient`, `subject`, `name`, `path`, `file`, `raw_`, `signal`, `waveform`, `secret`, `token`.
  - Truncates long lists (e.g. beat lists > 25 entries) into summary counts.
  - Clamps all numeric and string values to bounded lengths.

### 3.4 In-Memory Deterministic Caching
To minimize API consumption and deliver instantaneous responses when users re-inspect results:
- A canonical SHA-256 hash is computed over the composite of `model_id:prompt_version:sorted_json(payload)`.
- If a user clicks `Explain Results ✨` on an identical signal slice, the explanation is retrieved from memory immediately with a `⚡ Cached` badge.

## 4. Grounding and Medical Safety Guidelines

The system prompt (`SYSTEM_PROMPT` in `prompts.py`) enforces strict clinical safety rules:

1. **Non-Clinical Research Notice:** The system explicitly states it explains software outputs and algorithms, not patient medical health.
2. **Prohibition of Diagnostic Claims:** The model is forbidden from diagnosing myocardial infarction, ischemia, hypertrophy, or arrhythmias.
3. **Transparent 4-Class Taxonomy:** For Workflow C and Hardware Simulation, the model must explain the project-defined 4-class beat taxonomy (`N, S, V, Q; ventricular fusion F merged into Q`) and clarify that it is not an unqualified 5-class AAMI EC57 implementation.
4. **Hardware Simulation Disclosure:** For the AD8232 simulation, the explanation explicitly states that no physical sensor or Arduino is connected, and that baseline counts and gain are software approximations.
5. **Decoupled Optical Archival Notice:** For Workflow A, the model emphasizes that pixel traces have uncalibrated relative amplitudes and cannot be used for ST-segment measurements.
6. **Decoupled Evaluation Integrity:** When annotation matching is shown, the model explains that matching was performed strictly post-hoc (±50 ms tolerance) and that ground truth was not accessible during detection.

### Structured Output Schema
The response format strictly enforces 6 plain-language sections:
```json
{
  "simple_terms": "2-4 sentence non-expert overview explaining what the algorithm computed.",
  "what_numbers_mean": "Clear explanation of each probability score, count, or metric.",
  "what_stands_out": "Notable findings: class distributions, dominant patterns, clipping, or edge drops.",
  "limitations": "Specific constraints (short window, simulated transport, uncalibrated relative units).",
  "what_this_does_not_tell_you": "Explicit warning: Not a medical diagnosis, does not prove physical hardware operation.",
  "suggested_next_step": "Safe algorithmic next steps (inspect raw traces, test other records). Never medical advice."
}
```
